# 평점이 깎이는 지점 — Olist 주문 10만 건 분석

브라질 이커머스 Olist 공개 데이터로 **첫 구매 경험(배송, 리뷰)이 재구매로 이어지는지**, 그리고 **소비자의 불만이 생겨 판매자의 평점이 깎이는 지점**이 어디인지 확인한 프로젝트입니다.
결과를 보기 전에 판단 규칙(계획서 v1.2)을 먼저 정하고 그 규칙대로만 결론을 냈습니다. 결과를 본 뒤 추가한 분석은 "탐색"으로 구분했고, 가능한 것은 탐색 구간과 검증 구간을 나눠 확인했습니다.

- 탐색 화면: https://sohyeon1628-prog.github.io/olist-analysis/
- 분석 이야기(18페이지, 탐색 화면 캡처 포함): https://sohyeon1628-prog.github.io/olist-analysis/story.html

## 한 줄 요약
- 소비자는 마켓플레이스 이름으로 사고 Olist를 언급하지 않으며, 다시 사도 같은 판매자로 돌아오는 경우가 29%뿐입니다. 그래서 **소비자 재구매보다 판매자의 평점**을 지키는 관점으로 읽었습니다.
- 배송 지연은 부정 리뷰를 **6.9배** 늘렸지만, 재구매에서는 차이를 찾지 못했습니다(재구매가 드물어 상대 25~34%보다 작은 차이는 잡기 어렵습니다).
- 지연 말고도 평점이 깎이는 지점으로 **묶음 주문, 받기 전에 쓴 리뷰, 세일 시기**를 찾았습니다(탐색, 가설).

## 질문 재정의
| 확인 | 결과 |
| --- | --- |
| 고객 96,096명 중 2회 이상 주문 | 3.1% |
| 글이 있는 리뷰 40,809건에서 "Olist" 언급 | **0건** (마켓플레이스 이름 언급 1,944건, 4.8%) |
| 2회 이상 주문한 고객 2,913명이 첫 주문과 같은 판매자에게 다시 주문 | 29% (같은 카테고리 47%) |

"소비자가 Olist를 모른다"는 구조 설명은 가설입니다. 재구매가 드문 진짜 이유(구매 주기, 가격, 다른 채널)는 이 데이터로 구분할 수 없습니다.

## 계획한 질문의 결과 (대상: 2017-01 ~ 2018-02 첫 구매 고객 55,261명)
| 질문 | 비교 | 결과 | 판정 |
| --- | --- | --- | --- |
| ① 지연 → 부정 리뷰(1~2점) | 지연 65.4% vs 정시 9.5% | 6.9배, p < 0.001 | **차이 있음** |
| ② 지연 → 180일 재구매 | 지연 1.61% vs 정시 1.98% | -0.37%p (95% 구간 -0.80 ~ +0.05%p), p = 0.12 | 차이 없음 |
| ③ 부정 리뷰 → 180일 재구매 | 부정 1.68% vs 긍정 2.01% | -0.33%p, p = 0.061 | 차이 없음 |

- **"차이 없음"은 "영향 없음"이 아닙니다.** 전체 재구매율이 1.95%(1,080명)로 낮아, 확실히 잡을 수 있는 차이는 ②에서 상대 약 34%(0.67%p), ③에서 약 25%(0.50%p) 이상입니다. ③은 기준(0.05)에 가까운 경계선 결과였고, 미리 정한 규칙대로 "차이 없음"으로 판정했습니다.
- 카테고리, 구매 월, 결제 금액을 함께 넣은 로지스틱 회귀, 고객 지역(주)을 더 넣은 회귀, 리뷰를 뺀 회귀에서도 결론은 같았습니다 (`results/7_robustness_region.md`).
- 불만 주제(글이 있는 부정 리뷰 5,395건, 미리 정한 단어 사전): 지연 고객은 **"아직 못 받았다" 51.8%**, 정시 고객은 일부 누락 13.2%, 품질·파손 10.6%, 설명과 다름 10.4%.
- 모든 결과는 **관계**이고 원인이 아닙니다.

## 평점이 깎이는 지점 (계획에 없던 탐색, 가설)
| 지점 | 숫자 | 코드 |
| --- | --- | --- |
| **묶음 주문** | 여러 판매자 상품이 한 주문에 담기면 부정 리뷰 **47%**(상품 1개 12.7%). 배송 완료 + 정시 도착만 봐도 46.9% vs 7.5%. 부정 리뷰 글의 "일부 누락" 4.3% → 26.8~33.8%. 상품이 여러 개인 주문은 주문의 9.9%인데 부정 리뷰의 19.3% | `structure_evidence.py`, `multi_order_themes.py` |
| **받기 전에 쓴 리뷰** | 지연 고객의 **72.6%**가 상품이 도착하기 전에 리뷰를 씀(고객이 답한 시각 기준). 부정 비율 82.1% vs 21.3%. 요청 시점을 도착 후로 바꾸면 전체 부정 리뷰 약 2,700건(22%) 감소, 평균 별점 4.16 → 약 4.25 (단순 가정의 최대치) | `posthoc_review_timing.py` |
| **세일 시기** | 블랙프라이데이 주간(2017-11-20~27) 지연율 5.9% → **17.2%**, 부정 리뷰 12.0% → 20.1%. 주문량이 비슷한 달에도 지연이 달라 물량만으로는 설명되지 않음 | `structure_evidence.py` |

- 묶음 주문의 "나뉘어 도착"은 데이터에 분할 배송 여부가 없어 **가설**이고, 세일 시기는 블랙프라이데이 한 번의 사례입니다.
- 사후 발견 숫자는 처음 설문 발송일 기준(76.5%)으로 계산했다가 고객이 답한 시각 기준(72.6%)으로 바로잡았습니다. 방향과 결론은 같고, 정정 사실은 분석 이야기 한계에 적었습니다.

### 리뷰 글 감성 (BERTimbau, 탐색)
- 다른 브라질 쇼핑몰(B2W) 리뷰 8,000건으로 학습(Olist 별점으로 학습하면 별점과 비교할 때 순환 논리가 됨)
- 정확도 **98.2%** (별점을 가리고 글만 보고 판정한 정답 400건 기준, 같은 리뷰를 별점만으로 판정하면 96.4%). 사람이 50건을 따로 판정해 일치율 86.7%(카파 0.77) 확인
- ★4~5인데 글이 부정 8.1%, ★1~2인데 글이 긍정 5.4%
- 글을 남긴 첫 구매 고객만 보면 부정 고객의 재구매율이 낮음(글 1.77% vs 2.16%, p = 0.048). 결과를 본 뒤 추가한 분석이고 차이가 작아 결론은 바꾸지 않음

### 평점과 판매 (탐색 + 검증, 제안의 전제 확인)
- 상품의 처음 10건 주문의 평균 별점이 낮을수록 10번째 주문 뒤 30~120일의 판매가 적은가? 규칙을 검증 전에 확정(`results/rating_sales/rules.md`)
- 탐색(320개) 1.45배 (p = 0.014) → **검증(890개) 1.17배 (0.94~1.46), p = 0.158 → 확인되지 않음.** 검증 구간에서 평점 3분위별 이후 90일 평균 주문은 모두 6.8건

### 판매자 지속 (탐색 + 검증, 확인되지 않음)
- 판매자의 처음 10건 주문의 부정 리뷰율이 높을수록 이후 판매가 덜 이어지는가? 규칙을 검증 구간 결과를 보기 전에 문서로 확정(`results/seller/rules.md`)
- 탐색 구간(531명) 오즈비 0.75 (p = 0.003) → **검증 구간(293명) 0.88 (0.70~1.10), p = 0.272 → 확인되지 않음.** 표본이 작아 "관계가 없다"가 아니라 "판단 보류"

## 제안 (실험으로 확인할 것)
1. 리뷰 요청을 배송 예정일이 아니라 **실제 도착 후**에 보내기
2. 묶음 주문은 나뉘어 올 수 있다고 먼저 알리고, 리뷰는 **마지막 상품이 도착한 뒤**에 요청
3. 지연이 예상되면 먼저 알리고, 세일 전에는 판매자별 출고 능력 점검
4. 불만을 글로 남긴 고객에게 먼저 응대
5. 재구매는 구매 주기(중앙값 59일)에 맞춘 플랫폼 단위 리마인드로 따로 설계

제안은 "불만이 생기는 지점을 줄이는 실험"입니다. 줄이면 판매가 는다는 주장은 아닙니다(아래 한계).

한계: "평점이 판매에 영향을 준다"는 전제는 탐색·검증으로 확인해 봤지만 **검증 구간에서 뒷받침되지 않았습니다**(상품 초기 평점 +1점당 이후 판매 탐색 1.45배, p=0.014 → 검증 1.17배, 0.94~1.46, p=0.158). Olist 별점은 만족도 설문이라 고객에게 보이는 값인지도 알 수 없습니다. 제안은 "불만을 줄이는 실험"까지만 말합니다.

## 폴더 구조
```text
olist-analysis/
├── docs/                          # GitHub Pages
│   ├── index.html                 # 탐색 화면: "단계별 보기"(구매 → 재구매 추이·분포, 생키, 리뷰 원문)와 "집단별 비교"(기준 9개 × 열 7개 표 + 기준별 그래프 자동 배치), 해석 없이 사실만
│   ├── story.html                 # 분석 이야기 (한 화면에 한 페이지, 18페이지: 분석 결과 + 탐색 화면 캡처 + 사이트 소개·만든 방식)
│   ├── lab.html                   # 예전 주소 호환용(탐색 화면으로 이동)
│   ├── img/                       # 분석 이야기에 넣은 탐색 화면 캡처
│   └── data/                      # 조회용 데이터 (orders.js, reviews.js)
├── results/
│   ├── limits.md                  # 분석의 한계 (분석 이야기에서 분리한 본인 확인용 정리)
│   ├── summary.md                 # 계획한 질문의 결과 상세 (규칙 v1.2)
│   ├── 7_robustness_region.md     # 지역을 넣은 회귀
│   ├── 8_posthoc_review_timing.md # 받기 전에 쓴 리뷰, 규모 추정
│   ├── 9_multi_order_themes.md    # 묶음 주문의 불만 주제
│   ├── 10_structure_evidence.md   # 질문 재정의·묶음 주문·세일 시기 숫자
│   ├── seller/                    # 판매자 지속: 규칙(rules.md)과 결과
│   ├── rating_sales/              # 평점과 판매: 규칙(rules.md)과 결과
│   ├── sentiment/                 # 감성 분석: 판정 기준, 정답 세트, 모델 설정, 결과
│   ├── review_ko.json             # 리뷰 한국어 번역 (일부, Claude)
│   └── *.png, *.csv               # 그래프, 표, 불만 주제 표본 리뷰
├── analyze.py                     # 계획한 질문 분석 (규칙 v1.2)
├── robustness_region.py           # 지역을 넣은 회귀
├── posthoc_review_timing.py       # 받기 전에 쓴 리뷰
├── multi_order_themes.py          # 묶음 주문의 불만 주제
├── structure_evidence.py          # 질문 재정의·묶음 주문·세일 시기
├── seller_retention.py            # 판매자 지속 (탐색 + 검증)
├── rating_sales.py                # 평점과 이후 판매 (탐색 + 검증)
├── sentiment_*.py                 # 감성 분석 (정답 세트 추출 · 모델 학습/판정 · 결과 정리)
├── build_explorer.py              # 탐색 화면용 데이터 생성
├── translate_reviews.py           # 번역 묶음 합치기
└── requirements*.txt
```

## 실행
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
# Kaggle 원본 CSV 9개를 data/raw/ 에 넣은 뒤
.venv/bin/python analyze.py              # 계획한 질문 · 그래프
.venv/bin/python build_explorer.py       # 탐색 화면 데이터
.venv/bin/python structure_evidence.py   # 탐색 숫자 재현 (그 밖의 탐색 스크립트도 같은 방식)
```
감성 분석은 `requirements-sentiment.txt`(PyTorch, transformers)와 B2W 리뷰 데이터가 따로 필요하고, GPU 없는 맥에서 약 1시간 걸립니다.

## AI 활용
분석 코드, 웹 화면, 리뷰 번역, 감성 분석 정답 세트 판정은 AI(Claude)와 함께 작업했습니다. 리뷰 번역 중 23,431건은 Azure 기계 번역이며 화면에 "기계 번역"으로 표시합니다(무작위 100건 검사에서 뜻 오류 16%, `results/machine_translation_audit.md`).
정답 세트는 사람이 50건을 따로 판정해 일치율(86.7%, 카파 0.77)을 확인했습니다. 화면의 숫자는 모두 원본 데이터에서 코드로 계산한 값입니다.
